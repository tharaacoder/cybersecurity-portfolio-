# تنفيذ شبكة VoIP متكاملة — التركيز على Routing وDHCP
## (مشروع جماعي - حلقة بحث، بمسؤولية شخصية عن Router-on-a-Stick + DHCP)

## الهدف
كجزء من مشروع جماعي (4 طلاب) لتنفيذ شبكة VoIP كاملة على Packet
Tracer، كانت مسؤوليتي إعداد التوجيه بين Voice وData VLANs عبر
تقنية Router-on-a-Stick، وتهيئة خدمة DHCP لتوزيع IP تلقائيًا على
الهواتف والأجهزة — بما في ذلك الإعدادات الخاصة (Option 150)
اللازمة لعمل هواتف VoIP بشكل صحيح.

## سياق المشروع (جماعي)
مشروع "حلقة بحث" جماعي بمشاركة 4 طلاب، قُسّم لأربع مسؤوليات
متكاملة نظريًا وعمليًا:

- **Routing + DHCP** (دوري)
- إعداد الهواتف + مقدمة VoIP
- Voice VLAN + Switch Configuration
- QoS + Call Manager + Testing

سُلّم المشروع بثلاث مخرجات: عرض تقديمي (PowerPoint)، مشروع
Packet Tracer، وفيديو شرح مسجّل بصوت كل طالب عن جزئه.

## الأدوات
Cisco Packet Tracer

## بنية الشبكة (الجزء الخاص بي)
- راوتر مركزي (Router1) متصل بسويتش (Switch0) عبر رابط واحد يحمل
  VLAN البيانات (Data) وVLAN الصوت (Voice) معًا
- Sub-Interfaces على الراوتر لكل VLAN، لتفعيل مبدأ
  Router-on-a-Stick
- هاتفا IP (IP Phone2, IP Phone3) متصلان بالسويتش، وكل هاتف مربوط
  بجهاز كمبيوتر خلفه (PC0, PC1) عبر منفذ الهاتف الداخلي
- خدمة DHCP على الراوتر بـ Pool منفصل لكل VLAN

## الخلفية النظرية (من العرض التقديمي المرفق)

**VoIP (Voice over IP):**
تقنية تحوّل الصوت من إشارة تماثلية لبيانات رقمية، تقسّمها لحزم
(Packets) وترسلها عبر شبكة IP بدلاً من خطوط الهاتف التقليدية.
أبرز التحديات التقنية فيها: Latency (تأخير الوصول)، Jitter
(تذبذب زمن وصول الحزم)، وPacket Loss (فقدان حزم) — وكلها تؤثر
مباشرة على جودة المكالمة لأن الصوت يحتاج وصول فوري بدون انقطاع
(Real-Time Traffic).

**Voice VLAN:**
فصل حركة الصوت عن البيانات العادية بشبكة منطقية مستقلة، لضمان
أداء أفضل وأمان أعلى، وإعطاء أولوية لحركة الصوت داخل الشبكة.
البيانات العادية تتحمل التأخير، بينما الصوت لا يتحمله.

**Router-on-a-Stick وInter-VLAN Routing:**
عند وجود أكثر من VLAN، الأجهزة المختلفة الشبكات ما تقدر تتواصل
مباشرة، فيحتاج الأمر راوتر يربط بينها عبر واجهات فرعية
(Sub-Interfaces) — كل واحدة مرتبطة بـ VLAN محدد. هذا أشهر طرق
تنفيذ Inter-VLAN Routing باستخدام منفذ واحد بالراوتر لخدمة عدة
شبكات منطقية.

**DHCP وOption 150:**
يُستخدم بروتوكول DHCP لتوزيع عناوين IP تلقائيًا على الأجهزة، مما
يسهّل إدارة الشبكة ويقلل الأخطاء الناتجة عن الإعداد اليدوي. في
بيئات VoIP تحديدًا، يُستخدم خيار خاص يسمى **Option 150** لتزويد
الهواتف بعنوان خادم إدارة المكالمات (TFTP)، حتى تتمكن من تحميل
إعداداتها والتسجيل عليه تلقائيًا.

**Call Manager:**
مسؤول عن إدارة نظام الاتصالات بالكامل — تسجيل الهواتف على الشبكة،
تخصيص أرقام داخلية لها، تنظيم عملية الاتصال بين المستخدمين،
بالإضافة إلى توجيه المكالمات ومراقبة حالة الشبكة.

**Quality of Service (QoS):**
لضمان جودة المكالمات الصوتية، تُطبَّق تقنيات QoS للتحكم بأولوية
مرور البيانات داخل الشبكة. بما أن الشبكة تنقل أنواعًا مختلفة من
البيانات (فيديو، ملفات، تصفح، صوت)، فإن عدم إعطاء الصوت أولوية
أعلى قد يؤدي لتأخر وصول الحزم الصوتية وتشويش المكالمة أو انقطاعها.

## الخطوات (مسؤوليتي)
1. أنشأت Sub-Interfaces على الراوتر (Gig0/0.10, Gig0/0.20) وربطت
   كل واحد بـ VLAN مخصص عبر 802.1Q encapsulation
2. أعددت DHCP Pools منفصلة لـ Voice VLAN وData VLAN، كل واحد
   بمجال عناوين خاص فيه
3. فعّلت **Option 150** على DHCP Pool الخاص بالصوت — وهذا الإعداد
   الحرج اللي يخبر هاتف IP بعنوان TFTP Server عشان يقدر يحمّل
   ملفات الإعداد ويشتغل صح
4. تأكدت من حصول الهواتف والأجهزة على IP تلقائيًا من الـ Pool
   الصحيح حسب VLAN تبعهم

## ملخص خطوات المشروع الكامل (بالتعاون مع الفريق)
1. تصميم طوبولوجيا تضم راوتر، سويتش، هواتف IP، وأجهزة كمبيوتر
2. إنشاء VLANs لفصل حركة الصوت عن البيانات وتفعيل Trunk
3. إعداد الراوتر للتوجيه وDHCP وخدمة VoIP (دوري)
4. اختبار الاتصال بين الهواتف والتأكد من استقرار المكالمات

## الدروس المستفادة
فهمت عمليًا ليش VLANs المنفصلة (صوت وبيانات) تحتاج راوتر يتوسط
بينها حتى لو كانت على نفس السويتش الفيزيائي، ولماذا Option 150
تحديدًا حرج لعمل هواتف VoIP — بدونه الهاتف ياخذ IP بس ما يعرف وين
يحمّل إعداداته. كما أن نجاح نظام VoIP لا يعتمد فقط على وجود
الأجهزة، بل على تكامل عدة عناصر معًا: تصميم الشبكة، تقسيم VLAN،
التوجيه، توزيع العناوين، إدارة المكالمات، وتطبيق QoS.
